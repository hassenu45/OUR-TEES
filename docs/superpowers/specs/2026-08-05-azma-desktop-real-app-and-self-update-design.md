# AZMA Desktop — تطبيق حقيقي + تحديث ذاتي

التاريخ: 2026-08-05
الحالة: معتمَد (approved)

## الهدف

تحويل لوحة تحكم AZMA إلى **تطبيق حقيقي** على سطح المكتب (Electron) يعمل بنافذة أصلية — وليس متصفحاً — مع قدرته على **تحديث نفسه من داخل التطبيق** عبر سيرفر التحكم (نفس سيرفر Railway).

المشكلة الحالية: النسخة المثبّتة تفتح نافذة سوداء مع "404 Not Found" لأن ملف `app.asar` لا يحتوي ملفات الويب (`admin.html`, `js/`, `assets/`, `styles.css`...). التطبيق يعمل عند تشغيله من المصدر فقط، ولا يصلح كتطبيق حقيقي مثبّت.

## المبادئ الحاكمة

1. **تطبيق حقيقي**: نافذة Electron أصلية بدون متصفح خارجي، بدون شريط عنوان المتصفح.
2. **التحديث الذاتي**: التطبيق يفحص تحديثات عند الفتح تلقائياً + زر يدوي "تحقق من التحديث".
3. **التحديث يغطي ملفات الويب**: التحديث يطبق "حسب ما حدّث المستخدم" — ملفات الويب (admin.html, js/, css, assets). هذا يغطي 99% من التعديلات فوراً بدون إعادة تثبيت.
4. **البيانات عبر Railway**: المنتجات/الطلبات/الإعدادات تبقى تأتي من سيرفر Railway (proxy كالحالي)، مع fallback محلي مؤقت (localStorage) عند انقطاع النت — سلوك موجود حالياً في `js/api.js`.
5. **مصدر التحديث**: نفس سيرفر Railway — لا حاجة لسيرفر جديد.

## العمارة

### A. إصلاح 404 (أهم خطوة)

**السبب الجذري**: في `desktop/package.json`، قائمة `build.files` تشير لملفات خارج مجلد `desktop/` بـ `../admin.html` إلخ. لكن electron-builder لا يضمّن ملفات من خارج مجلد التطبيق بهذه الطريقة — فالمعلّب الناتج يحتوي فقط `main.js`, `package.json`, `preload.js`. وعند تشغيل النسخة المثبّتة، `PROJECT_ROOT = path.resolve(__dirname, '..')` يشير لمكان غير صحيح، والسيرفر المحلي يطلب `admin.html` فيرد 404.

**الحل**:
- إضافة مجلد `desktop/web/` يضمّ نسخة من ملفات الويب، تُبنى بأمر `npm run build:web` (سكربت نسخ من جذر المشروع: `admin.html`, `hub.html`, `login.html`, `index.html`, `store.html`, `designer.html`, `designer_debug.html`, `21.html`, `orders.html`, `styles.css`, `js/**`, `assets/**`, `manifest.json`).
- `desktop/web/` يُضمّن في `build.files` كـ `"web/**/*"`، ويُضاف لـ `.gitignore` (لأنه ناتج بناء).
- `main.js`: `PROJECT_ROOT` يصير `path.join(__dirname, 'web')` في النسخة المعلّبة (و`__dirname`+`../web` عند التطوير)، مع `try/catch` للعودة للجذر القديم في وضع التطوير.

**خيار التخزين القابل للكتابة**:
- مجلد `userData/web` هو المكان الفعلي الذي يخدم منه التطبيق الملفات.
- عند أول تشغيل: إن لم يوجد `userData/web/manifest.json`، يُنسخ `desktop/web/**` إليه (النسخة المدمجة).
- عند الطلب: يخدم السيرفر المحلي من `userData/web` أولاً، فإن لم يوجد الملف هناك → يقع على النسخة المدمجة `desktop/web`.

### B. نقطة التحديث على السيرفر (server.js)

نضيف مسارين في `server.js`:

1. `GET /updates/manifest.json`
   - يقرأ ملف `VERSION` (مكتوب في جذر المشروع، رقم النسخة الحالية — نصي، مثل `1.0.0`) إن وُجد، أو `package.json.version`.
   - يحسب `sha256` لحظياً لكل ملف ويب منشور على السيرفر (قائمة ثابتة: الملفات المذكورة أعلاه + `assets/**` و `js/**` و `assets/css/**`).
   - يرد JSON:
     ```json
     {
       "version": "1.0.0",
       "files": [
         { "path": "admin.html", "sha256": "…", "size": 1234 },
         { "path": "js/api.js", "sha256": "…", "size": 99 }
       ]
     }
     ```
   - يُخدم بدون مصادقة (التحديث يحتاج الوصول العام؛ الملفات نفسها ليست سرّية — لوحة التحكم نفسها متاحة للعموم بصفحتها).

2. `GET /updates/file/<path>`
   - يخدم ملف ويب مفرد من جذر المشروع، بعد التحقق أن المسار ضمن الحدود (منع directory traversal بنفس منطق ALLOWED_STATIC_EXT و `path.normalize` + prefix check).

- `VERSION` في جذر المشروع: ملف نصي بسيط يُزاد يدوياً (أو تلقائياً) عند كل نشر. في البداية نكتب `1.0.0` ونوثّق رفعه يدوياً.

### C. محرك التحديث في التطبيق (desktop/main.js + preload.js)

مكون جديد في `main.js` (أو ملف `updater.cjs` مستورد من `main.js`):

- **فحص التحديث** (`checkForUpdates`):
  1. `fetch(`${PROD_BASE}/updates/manifest.json`)`.
  2. إن فشل الاتصال أو المانيفست غير موجود → نتيجة `{ updateAvailable: false, error: '…' }` (بدون مقاطعة).
  3. قارن `version` مع `manifest.json` المحلي في `userData/web`.
  4. لو النسخة أحدث: قارن `sha256` لكل ملف، اجمع الملفات المتغيرة.
  5. نزّل الملفات المتغيرة من `/updates/file/<path>` (مع حد أقصى للحجم لكل ملف، وإلغاء عند تجاوز المجموع).
  6. تحقق من `sha256` لكل ملف محمّل — أي تطابق خاطئ → رفض الملف وإلغاء التحديث كاملاً (rollback: لا تُكتب أي ملفات ناقصة/فاسدة).
  7. اكتب الملفات الجديدة في `userData/web` بشكل ذري (اكتب إلى ملف مؤقت ثم انقل/استبدل).
  8. حدّث `userData/web/manifest.json` بالنسخة الجديدة.
  9. أعد تحميل النافذة (الإخطار بالواجهة أولاً).

- **الواجهة**: زر "تحقق من التحديث" في لوحة التحكم (admin.html) يعرض حالة (آخر إصدار، تقدم التنزيل، "تم التحديث — سيُعاد التحميل").

- **قناة IPC** عبر `preload.js`:
  - `window.azma.checkForUpdates()` → يبدأ الفحص، يُرجع `{ checking, updateAvailable, version, progress, done, error }`.
  - `window.azma.onUpdateProgress(callback)` → أحداث تقدم.

### D. الحفاظ على "تطبيق حقيقي"

- لا تغيير على سلوك النافذة (لا قوائم متصفح، `Menu.setApplicationMenu(null)`, حماية التنقل).
- لا يتطلب التحديث إعادة تثبيت NSIS إلا إذا تغيّر قلب Electron نفسه (خارج نطاق هذا التصميم).
- التطبيق يعمل محلياً بدون إنترنت: الملفات من `userData/web`، والبيانات fallback محلي.

## الملفات المتغيرة

| الملف | التغيير |
|---|---|
| `desktop/main.js` | إصلاح `PROJECT_ROOT` ليشير لـ `web/`؛ إضافة محرك التحديث؛ توجيه `/updates` للفحص |
| `desktop/preload.js` | فتح قنوات IPC للتحديث |
| `desktop/package.json` | إضافة `web/**/*` إلى `build.files`؛ سكربت `build:web` |
| `desktop/web/` (جديد) | نسخة ملفات الويب (ناتج بناء، مجمّد في .gitignore) |
| `server.js` | إضافة `/updates/manifest.json` و `/updates/file/*` |
| `VERSION` (جديد) | رقم النسخة الحالية، في جذر المشروع |
| `admin.html` + `js/admin.js` | زر "تحقق من التحديث" + مؤشر الحالة |
| `.gitignore` | تجاهل `desktop/web/` |
| `docs/` | هذه المواصفات |

## معالجة الأخطاء

- **انقطاع النت**: الفحص يفشل بهدوء، التطبيق يعمل بالنسخة المحلية كالمعتاد.
- **ملف فاسد (hash mismatch)**: يُرفض، التحديث يُلغى، تبقى النسخة القديمة سليمة، يظهر خطأ واضح.
- **مسار خبيث في التحديث**: `path.normalize` + التحقق من البادئة داخل `userData/web`؛ رفض أي ملف خارج النطاق.
- **مساحة/حجم**: حد أقصى لكل ملف (مثلاً 50MB) وللمجموع (مثلاً 300MB).
- **تحديث أثناء تشغيل**: لا حاجة لإعادة تثبيت؛ فقط إعادة تحميل النافذة.

## خطة التحقق (Verification)

1. **وحدة هاش**: اختبار Vitest `tests/updater.test.js` — حساب sha256، بناء المانيفست، مقارنة ملفات متغيرة.
2. **اختبار السيرفر**: `GET /updates/manifest.json` يُرجع JSON صالح بملفات متوقعة؛ `GET /updates/file/admin.html` يعيد المحتوى الصحيح؛ رفض `../` (403).
3. **اختبار يدوي (desktop)**: `npm run build:web` ثم تشغيل النسخة المعلّبة (win-unpacked) — يجب أن تفتح لوحة التحكم بدون 404.
4. **اختبار التحديث اليدوي**: رفع نسخة جديدة (تغيير `VERSION` + ملف) إلى Railway → فتح التطبيق → فحص تلقائي يجدها → تنزيل → إعادة تحميل تعرض النسخة الجديدة.
